# SigmaLink v3.1.0

**Hardware-load release.** Apple Silicon Macs were being auto-updated onto the Intel build and translated through Rosetta — this fixes the routing, cuts the package by a third, and contains a 1.57 GB Windows RAM leak. Plus a session-persistence and pane-reliability round.

---

## ⚠️ Read this first if you are on an Apple Silicon Mac

**You may need one manual install. Your updater cannot rescue you.**

Every release through v3.0.0 served the **x64 (Intel) DMG to every Mac**, including Apple Silicon. `latest-mac.yml` lists the x64 asset first, and the old updater took the first `.dmg` it saw with no architecture check. If you have been updating in-app, **you are almost certainly running the Intel build under Rosetta** — costing ~468 MB of translation arenas plus a CPU and battery tax.

The fix ships *in* this release, which means it cannot fix the update *to* this release. To escape:

1. Download **`SigmaLink-3.1.0-arm64.dmg`** below — by hand, not through the in-app updater.
2. Replace your existing `/Applications/SigmaLink.app`.
3. Verify: `lipo -archs /Applications/SigmaLink.app/Contents/MacOS/SigmaLink` must print `arm64`.

Every update after this one routes correctly on its own.

## ⚠️ Platform matrix cut to two targets

**v3.0.0 was the last release for Intel macOS and for Linux.**

- **Intel (x64) macOS — retired.** Every Mac Apple has shipped since 2020 is Apple Silicon. An Intel Mac will not receive further updates and cannot run the Apple Silicon build.
- **Linux (AppImage + `.deb`) — retired.** This retires *artefacts*, not code: the ubuntu CI jobs still run on every PR and a self-built Linux tree still works.
- **Windows x64** is unchanged. (x86/ia32 was dropped back in v1.2.0.)

## Fixed — the release-blocking ones

- **macOS auto-update served the wrong architecture to every Mac.** Asset selection now resolves the *effective* arch (seeing through Rosetta via `runningUnderARM64Translation`, since `process.arch` reports `x64` inside a translated process) and picks the matching DMG. The fallback is deliberately asymmetric: an Apple Silicon host may accept an x64 asset so older releases stay updatable, but an Intel host is **never** handed an arm64 build it cannot execute. (#247)
- **macOS panes would have failed to spawn.** The packaging change moved `node-pty`'s `spawn-helper` into `app.asar.unpacked`, where it arrived without its executable bit. The signing hook now restores mode `0755` and **throws** if it cannot find the helpers, rather than silently shipping a build whose every terminal is dead. (#250)
- **Windows: ~1.57 GB RAM leak from stdio MCP sessions.** Contained by a RAM brake with a second admission pass over observed process state. (#251)
- **Windows: `shell-first` PTY spawn was defaulted on without ever being dogfooded.** Now platform-aware — unset resolves to `direct` on win32. (#250)
- **Operator-copyable commands were unquoted.** A path containing a space or quote broke the External Control connect command; the cursor-agent install line rendered as `bash -c curl <url> | bash` and silently did nothing. All routed through one shared quoter with real `CommandLineToArgvW` semantics on win32. (#248, #253)
- **Windows process trees were stranded.** Pane teardown killed only the root pid, leaving descendants alive. (#254)

## Fixed — panes, sessions, reliability

- **Relaunch resumed the *old* session** — four stacked causes: a quit-race stranding rows in `error`, slot-blind boot resume, a relaunch leak, and rename loss. (#240)
- **Codex panes showed "Pane crashed" over a live terminal.** A content scanner was reporting through the process-death channel; it now has its own advisory channel and the pane stays running. (#239)
- **Claude account switches propagate** to live panes instead of leaving them on stale credentials. (#238)
- **Pane rendering stabilized** + persistent drag reordering. (#246)
- **Kimi Code pane compatibility** — launch, flicker, labels, migration fallout. (#245)
- **Windows shells survive CLI exit.** (#242)
- **Notification state hydration** made authoritative and race-safe. (#244)

## Changed

- **Package is ~30% smaller** — 380 MB → 266 MB (arm64), with `asar` restored and native modules in `app.asar.unpacked`. An `afterPack` guard now asserts every keep-list module actually landed, so a dependency swap can no longer silently drop a native helper. (#247)
- **Renderer memory tuning** — centralized scrollback limits, trim-on-park, and a `pty.scrollbackRows` setting. (#247)
- **Pane header drops the effort tier.** `<name> · high` no longer renders in the title pill; the value stays in the pill tooltip, the gear popover and the context sidebar. (#257)

## Measured, and what the numbers do *not* say

Native arm64 vs the same workload under Rosetta, on an M4:

| | x64 (Rosetta) | native arm64 |
|---|---:|---:|
| total footprint | 3338 MB | **1761 MB** |
| Rosetta translation arenas | 468 MB | **0** |

**The −47% total is not a controlled comparison** — the two runs were at 17 and 14 panes respectively, and the x64 install no longer exists to re-measure. Treat it as indicative. The clean, pane-count-independent result is the **468 MB → 0** on translation arenas.

Full data: `app/docs/perf/2026-07-28-arm64-baseline.md`.

## Known limitations

- **The RAM saving from renderer tuning is unmeasured.** The trim constants were calibrated against the 1684 MB x64 renderer figure; the measured native-arm64 working set for that renderer is ~336 MB dirty, of which ~261 MB is V8/Blink heap. Tracked as C-067.
- **`e2e-matrix` flakes at roughly 1 run in 4.** Tracked as C-066.
- Descendant-process reaping on a stale table is deliberately left open — the specified fix would SIGKILL stale PIDs (C-063).
